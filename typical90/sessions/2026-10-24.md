## What `[lx, rx] × [ly, ry]` means

The Japanese is `左下角` (lower-left corner) and `右上角` (upper-right corner). The naming is positional-then-axis:

```
lx = x of the LEFT edge       rx = x of the RIGHT edge
ly = y of the BOTTOM edge     ry = y of the TOP edge
```

So the box is $x \in [lx, rx]$, $y \in [ly, ry]$, and since $x$ and $y$ live on perpendicular axes:

$$\text{width} = rx - lx, \qquad \text{height} = ry - ly$$

`lx - ly` mixes the two axes, so there's nothing for it to mean. Width comes from `rx - lx` only.

**And there is no `+1` anywhere.** The `+1` belongs to counting *lattice points*: how many integers $x$ satisfy $1 \le x \le 3$? Three, i.e. $3 - 1 + 1$. But this problem asks for **area**, and `[1,3]` has length $2 = 3 - 1$. The unit cells I drew are just bookkeeping — cell `x = 2` covers `[2,3)` — and because the cell index is the *left* endpoint, the exclusive `rx` already accounts for everything.

## What "exactly $k$" means

Not an intersection over a growing prefix. All $N$ sheets are laid down **once**, all at the same time. Then every point of the plane gets a number: how many sheets sit on top of that point. $A_k$ is the total area of the points whose number is **precisely** $k$.

Your reading is a different (also interesting) problem: the intersection of the first $k$ rectangles, which is non-increasing. Two things to hold against it:

**Sample 3 refutes it outright.** Its first outputs are `1806, 990, 1013, 1221, ...` — the sequence *rises* at $k = 3$. A prefix intersection can't rise, and neither can an "at least $k$" area (which is $\sum_{j \ge k} A_j$). Exactly-$k$ answers are free to go up and down; that's the whole reason you have to keep a separate bucket per count.

**Two checks you can run on any instance:**

$$\sum_{k} A_k = \text{union area}, \qquad \sum_{k} k \cdot A_k = \sum_i \text{area}(\text{sheet } i)$$

Sample 2 is the quick sanity pass: `1 1 3 4` ($2 \times 3 = 6$) and `3 4 6 5` ($3 \times 1 = 3$). They touch only at the single point $(3,4)$ — zero area — so $A_1 = 9$, $A_2 = 0$. Union $= 9$, and $\sum k A_k = 9 = 6 + 3$. ✓

## The convention

The disorientation isn't something to manage — it's something to delete. It comes from one smuggled assumption: **that the array is a picture of the plane.** It isn't. In a geometry problem the array is a *lookup table keyed by coordinates*, and nothing more.

| in the plane | in the array |
|---|---|
| unit square `[x, x+1) × [y, y+1)` | `a[x][y]` |
| corner worth `d` at `(x, y)` | `a[x][y] += d` |
| origin-anchored prefix over `x' ≤ x, y' ≤ y` | accumulate in **increasing index**, per axis |

Three rules fall out, and each one kills a different piece of the confusion:

**1. Never name an index `row` or `col` in a coordinate problem.** Name it `x` and `y`. "Row 0 is at the top" is a fact about *screens*. "`y = 0` is at the bottom" is a fact about *the statement*. They have no relationship, and the moment your variable is called `row`, your brain imports the screen without asking.

**2. Pass direction is set by the prefix definition, not by gravity.** `Σ_{x'≤x, y'≤y}` runs in increasing index on both axes. There is no top/bottom decision anywhere — the only real question is *which index is accumulating*, and both passes answer it identically.

**3. The transform is symmetric under swapping the two axes.** Writing `a[y][x]` with the coordinates also swapped gives the identical answer. So which index you call `x` cannot change correctness — only whether you can read your own code.

That third point is why your file works despite the headache. Look at what you actually wrote:

```cpp
grid[lx][ly] += 1;      // first index is lx -> first index is x
grid[lx][ry] -= 1;
grid[rx][ly] -= 1;
grid[rx][ry] += 1;
```

The first index *is* x. The code was never confused. Only the names were:

```cpp
for (int r = 0; r < MAXN; ++r)   // 'r' is actually x
  for (int c = 1; c < MAXN; ++c)
    grid[r][c] += grid[r][c - 1];   // ...accumulating over y, called 'c'
```

Rename and the file reads like the statement:

```cpp
// grid[x][y] = sheets covering the unit square [x,x+1) x [y,y+1)
grid[lx][ly] += 1;  grid[lx][ry] -= 1;
grid[rx][ly] -= 1;  grid[rx][ry] += 1;

for (int x = 0; x < NMAX; ++x)      // prefix along y
  for (int y = 1; y < NMAX; ++y) grid[x][y] += grid[x][y - 1];
for (int y = 0; y < NMAX; ++y)      // prefix along x
  for (int x = 1; x < NMAX; ++x) grid[x][y] += grid[x - 1][y];
```

One exception worth naming so you don't over-apply this: when the grid arrives *as* a picture — a maze of `#` and `.`, a board of characters — then it genuinely is a picture, and `row`/`col` are the honest names. The rule is just **name the index after what it actually is**: coordinates when they came from geometry, row/column when they came from an image of a grid.

## Why there is no orientation to agree on

This problem gave you no grip because it doesn't *have* an orientation. Not "we should pick one carefully" — there is nothing to pick. Write down what the problem actually is:

$$\text{cnt}(x,y) \;=\; \sum_i [\,lx_i \le x < rx_i\,]\cdot[\,ly_i \le y < ry_i\,]$$

There is no up, down, left, or right in that expression. Only `≤` and `<`. Swap $x \leftrightarrow y$ and $(lx,rx) \leftrightarrow (ly,ry)$ everywhere, and the expression comes back **identical**. So the transform is symmetric under the swap: any correct solution under one axis naming is a correct solution under the other, with the two indices exchanged. The labeling is not information — it's the order you happened to type things in.

So the axis assignment cannot be wrong. What can be wrong is **uniformity**:

> The one real rule: all four corner writes must agree about which index carries $x$. Mechanically — in each of the four lines, the first index comes from $\{lx, rx\}$ and the second from $\{ly, ry\}$. All four, or it's not a rectangle.

That's the check you can run with your eyes, and it's the only thing that matters. Take the four writes and transpose just one of them — say `grid[ry][rx] -= 1` for the third — and the thing you've built isn't a rectangle at all. No prefix pass recovers it.

**The picture is a rendering; the inequalities are the source of truth.** When the two disagree, the picture is the one that's lying — which is the whole story of the next section.

And when *does* an axis genuinely have a role? Only then is a convention needed, and it must be chosen once.
